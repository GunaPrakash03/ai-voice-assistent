1. First run

  1. Start the stack (section 10) and open the site. With no password on file it shows Create your admin sign-in: confirm your email and choose a password (8+ characters).
  2. Open API Keys & Providers and add at least Deepgram (speech) and Google Gemini (dialogue). See section 2.
  3. Open My Profile, set your name and phone, and add your teammates (section 4).
  4. Build or review the live agent, then set a phone number to route to it (sections 5 and 6).

2. Provider keys admin only

Keys are saved to the server's .env file and loaded into the running server immediately. The agent worker container reads .env only at start, so restart it after adding a key that live calls need (Gemini, ElevenLabs): docker compose up -d agent.

3. Model & voice plans

  • Gemini 3.5 Flash Lite is the default: good enough for intake and the most generous free-tier rate limit. Gemini 3.6 Flash is smarter but limited to 5 requests per minute on the free tier, which a live call exceeds. Retired ids (gemini-2.0, 1.5) are remapped automatically.
  • Voices that are real today: all ElevenLabs premade voices, all Deepgram Aura voices, and the Neural Voice entries in the browser. Live calls stream ElevenLabs and Aura only; anything else falls back to Aura with the reason logged and shown to the caller-side log.
  • The voice picker's Sync accounts pulls voices you add to your ElevenLabs account; Real voices only hides fallbacks.

4. Team & roles

On My Profile → Members add a member with name, email, optional phone, role and a temporary password. They change the password on their own profile. Remove deactivates the account and ends its sessions. The workspace always keeps at least one admin.

RoleSeesCan do
AdminAll agents, all calls, all settingsEverything, including API Keys & Providers and members
UserAll agents and all callsWhole dashboard: build, test, set live, route numbers, webhooks, call history. Cannot open API Keys & Providers or manage members
Sharing model: agents, calls and webhooks are shared across the workspace. Every signed-in member can open and edit any agent; the only admin-only areas are the API Keys & Providers page, member management, the admin guide and the cost comparison.

5. Agents overview

The Agents tab lists every agent with its owner. Set live chooses the agent that answers calls without specific routing; only one agent is live at a time. Edit opens any agent in the builder. Each save keeps a revision; the builder can roll back.

Test calls, recordings and extracted data are attributed to the agent that handled them, and every member sees the same call history.

6. Numbers & SIP trunks

  1. Buy Phone Numbers: Telnyx and Twilio inventory in separate tabs; buying records the carrier, assigns a trunk and an agent.
  2. SIP Trunks & DIDs: owned numbers with an agent dropdown each (per-number routing), inbound and outbound trunks, and dispatch rules. Edit or remove numbers and trunks here.
  3. The live worker reads the dialled number on an incoming SIP call and answers with the agent assigned to it; unassigned numbers use the live agent.
Real calls need a SIP gateway. The compose stack runs LiveKit, Redis, Postgres and the worker but no LiveKit SIP service yet, so outbound dialling and inbound calls to the Twilio number are simulated. To go live: add the livekit/sip container, expose it on a public address, and point the Twilio (or Telnyx) trunk at it.

7. Webhook endpoints

On Webhooks & Data add an endpoint URL, choose events, and optionally set the signing secret (one is generated otherwise). Press Test: a signed test event is posted and the result shows the HTTP code and round trip. The health pill reflects the last delivery. Recent deliveries list status, attempts and errors, with Replay.

Endpoints are workspace-wide; whether a call posts anything is decided per agent by its Webhook & data extraction toggle. The payload carries call, extracted (the agent's fields, filled by Gemini), summary, sentiment and transcript, signed with X-Signature-256 (HMAC-SHA256 of the body). Failed deliveries retry with back-off, then land in the dead-letter list.

8. Storage & backups

Everything is written through to PostgreSQL (container voice-postgres, host port 5433, volume voice_pgdata): agents and revisions, phone numbers, trunks and rules, users, sessions and API keys, post-call jobs, and every recording as bytes. The JSON files under config/ and the WAVs under recordings/ remain the working copy; at start-up anything missing or older on disk is restored from the database.

  • Connection: DATABASE_URL in .env (empty = files only).
  • Status: My Profile → Data & storage, or GET /api/storage/status.
  • Backup: docker exec voice-postgres pg_dump -U voice voice_agent > backup.sql.
  • If you edit a config JSON by hand, restart the server afterwards, otherwise the newer database copy is restored over it.

The pipeline's archive copies in recordings/archive/ carry a placeholder s3:// URL; there is no cloud upload yet.

9. Sign-in & security

  • Passwords are stored as PBKDF2-SHA256 hashes. Sessions are HttpOnly cookies (12 h, or 30 days with "keep me signed in") and are stored hashed.
  • The SMS step is on for any account with a phone on its profile. Codes last 5 minutes, 5 attempts, resend after 30 s. Sender: the workspace's SMS-capable Twilio number (TWILIO_SMS_FROM overrides).
  • Every page redirects to sign-in when signed out. JSON API calls from this machine are allowed without a session so the test suites and tools keep working; set AUTH_TRUST_LOOPBACK=0 in .env to require a session everywhere.
  • Provider keys and member management are admin-only on the server, not just hidden in the UI.

10. Running the stack

docker compose up -d redis livekit postgres agent   # media server, cache, database, AI worker
python3 scripts/serve.py                            # dashboard + API on http://localhost:8091
docker compose up -d agent                          # restart the worker after key changes
docker compose logs -f agent                        # live worker log (voice engine, dialogue backend, tool calls)
python3 scripts/run_all_tests.py                    # 20 verification suites
  • Live suites (1.4, 1.5, 1.6, 1.7, 2.5, 2.6) can flake when anything else touches LiveKit at the same time; rerun one alone before calling it a regression.
  • The worker logs Agent '…' loaded for this call with the dialled number, voice engine and any fallback reason, and Dialogue backend: gemini when the model is connected.
